## 1. 目标与范围

在 Mac Pro 上自建文献语义检索系统（**复刻 WisPaper 的检索层架构**；其验证层由 Zcode agent 承担——据 arXiv:2512.06879，WisPaper 的增益含 Deep Search 逐篇验证（validation accuracy 93.70%），非向量检索单独贡献，X-4 口径）：
- 语料：PubMed 2026 baseline 全量（约 4000 万题录 / 2950 万摘要），每日 updatefiles 增量
- 查询：中文自然语言（两条并行腿：Zcode 翻译后英文检索式为主 + 模型多语能力中文直查为零成本备用腿，N-9）→ 英文文献
- 检索：Qwen3-Embedding-8B 稠密 + BM25 稀疏 + RRF + cross-encoder 精排
- 场景：日常调研、SR title/abstract 筛选加速（gold set 召回验证）、找暗相关文献

**定位边界（X-4/X-5 强化）**：本地库 = 筛选加速与日常调研，**不作为 SR 检索的数据库报告**。WisPaper 自报 TaxoBench recall 22.26%（vs O3 20.92%）——绝对召回天花板提醒：向量检索不保障 SR 召回完备性。SR 合规四条：① PRISMA-S 要求逐库报告检索式与日期，本地库不得列为"检索的数据库"；② Cochrane 最低库集 = MEDLINE + Embase + CENTRAL + 试验注册库（Embase 商业库永无 bulk 通道）；③ 用 ASReview 须在 Methods 披露软件版本/特征模型/停止规则/是否双人核查；④ 论文写法用 `PubMed (MEDLINE)`（PubMed 含非 MEDLINE 记录）。

裁剪项（WB 认可维持，N-6 重排后）：全文 ColBERT 层（存储爆炸）、LLM 卡片蒸馏（PubMed 元数据+MeSH 已结构化）；**不裁** MeSH 同义词/查询扩展腿（成本≈0）。

| 数据层 | PubMed baseline 2026 + updatefiles 每日增量（P0-P2 唯一数据源） | P3 才引入 PMC OA / OpenAlex / S2AG |

## 5. 分阶段实施（增补 §6 重排：P0+P1 合并连续跑）

### P0+P1 · 合并连续跑（一次 GPU 占用完成，预计 1-2 天）

**GPU 前连续编排（C-2 + 增补 §3 全文落地）**——每步断言落盘（时间戳+返回码），禁止只写"全自动"：

- **Step 0 前置断言**：`nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv` 确认唯一消费者为 vllm-nvfp4 两 Worker；`tmux ls` 记录在案（避开 `embed` 会话名——那是记忆库资产，不得误 attach/干扰）
- **Step 1 持续禁看门狗（整个连续周期）**：`sudo systemctl stop vllm-watchdog.timer`——`OnCalendar=21:10 + Persistent=true` 的 watchdog 不知道编码任务存在，多天连跑必撞 21:10 或唤醒补跑把 vLLM 拉起来抢显存。**睡眠 automation 停了 ≠ watchdog 停了，独立对象**。完成前保持停用，结束才恢复
- **Step 2 停容器+显存断言**：`sudo docker stop vllm-nvfp4`（unless-stopped 策略 ⇒ 手工停不会被自动拉起；**以 `docker inspect` 复核 RestartPolicy 后再执行**，WB 未能实测此项）；`nvidia-smi --query-gpu=memory.used --format=csv,noheader` 断言每卡 < 500 MiB（沿用睡眠 automation 既有阈值口径）
- **Step 3 启动+自描述落盘**：专用 tmux（非 embed 名）；落盘脚本 md5、语料清单 md5、**预期总 token 数**、起始时间戳；8001 停用期间 Macx 主力走在线模型（裁定 3）。**影响面（e2①）**：local-vision MCP → 8001 的本地视觉链路同停，图片/视频识别改走 zai-vision 在线（≤5MB 硬墙，超限先过 `compress_for_vision.py`）
- **Step 4 运行期巡检（30-60 分钟一次，脚本化）**：GPU 温度/功耗/显存/降频（`nvidia-smi -q -d PERFORMANCE`）；`df -h /home`；进度=已编码条数 vs 预期（实时 tok/s 与 Step 3 预测对账）；**`systemctl is-active vllm-watchdog.timer` 断言 == inactive（e2③，防静默复活——连跑几天，一次静默复活就够毁掉一整轮）**；**检查点每 N 万条落盘可续跑**——连跑数天崩了不能从头来
- **Step 5 收尾**：`docker start vllm-nvfp4` + `systemctl start vllm-watchdog.timer` + `curl localhost:8001/v1/models` 断言 200；输出锚点表（tok/s、条/s、总耗时、实际 token 总数 vs 预测）

**技术工作清单**（GPU 占用与 CPU 工作并行）：
1. Qdrant 容器：**版本 ≥1.19（C-4）**——v1.19 `memory`（pinned/cold 分层，量化向量可落盘）、v1.18+ TurboQuant（4/2/1-bit，Cosine/Dot/L2 全支持）直接命中本场景
2. MedRAG 语料抽 10 万条 → vLLM `--runner pooling` 双卡起 8B：bf16 编码 1 万条（吞吐锚点，**单卡与双卡各记一组**，X-1）；同批 FP8 动态量化（`--quantization fp8`）再编码 → cosine 一致性 + gold set 检索对比 → **定 P2 用 bf16 还是 FP8**
3. **MedCPT 对照臂**（C-1）：同批语料 MedCPT 编码 → gold set 召回对比，"通用 8B ≥ 领域专训"补实测凭证
4. **Qdrant 负载测试（C-4 独立维度，e2② 成本控制）**：矩阵 = 量化方法（int8 / 4-bit / 2-bit / 1-bit TurboQuant）× memory tier（pinned/cold）共 8 组——**先在 5-10 万篇子集上筛全矩阵，只在胜出的 1-2 组上做 54 万篇全量验证**（结论不变、省 8× 灌库时间）。binary 类量化要求向量分量中心化分布，Qwen3 系未经官方验证，**必须实测不得假定**
5. 下载 baseline 50.9GB（走代理）→ MeSH 过滤（词表与课题对齐）→ **P0 无条件落盘两个数（N-5）：无 MeSH 记录占比 + 其 publication type/年份分布**（出版社直供/ahead-of-print/作者手稿永无 MeSH，会被过滤系统性排除——确认筛掉的不是 SR 必需类型。附：MTIX 后 PubMed 索引延迟≈1 天，时效性无忧）
6. 54 万篇 8B 编码（双卡 8k tok/s 估 5-6 小时【推测，实测修正】）→ 建 collection（PMID 为 ID）
7. 稀疏腿验证（N-1）：fastembed + Qdrant/bm25 依赖就位检查 + 生医语料稀疏召回合理性
8. **gold set 召回测试（N-9，替代原 sanity check 的方法学部分）**：用 **sICH R3 / aSDH SR 的 included studies** 作 gold set（零成本、真实分布），测 recall@20/50/100 + 已知必纳文献**排名分布**（不只记有无进 top-k）；对照臂：中文直查 vs 翻译后英文；长查询 vs 短查询（翻译前置易产关键词密集长串，测 dense 腿受损度）；工程断言：instruction 格式、dense/sparse 分腿构造、**模型一致性（两侧 model_id+dim 打印，不等即 abort）**
9. reranker 盲评（N-2）：bge-reranker-v2-m3 vs Qwen3-Reranker-0.6B，50-100 条人工盲评定型（Qwen3-Reranker 分数以其官方报告为准，P0 现场核实）
10. SR 导出验证：CSV 接 ASReview

**P0/P1 结束时交付**：本领域生产可用检索 + 实测锚点表（tok/s 单/双卡、Qdrant 负载数据、FP8 比对结论、MedCPT 对照结论、gold set 召回率）+ **P2 确定排期**（实测 tok/s × 全量 token 数，X-3）→ 请 Macx 裁定 P2 启动

### P2 · 全生物医学（**独立决策闸门后启动**）

1. 全量解析：40M 题录 / 29.5M 摘要 → JSONL（~15GB）；P0 顺带**精确统计全量 token 数**（WB 估算 7.4-11.8B token）
2. 排期两档（连续 24h）：bf16 11-17 天 / FP8 6-9 天（X-3 修正后量级；实测后定）——期间 8001 停用、watchdog 全程禁用、检查点续跑
3. **存储/内存方案（C-3 修正，P0 负载数据二选一）**：
   | 方案 | 向量内存占用 | 说明 |
   |---|---|---|
   | 4096d fp16 | 242 GB | 超 153GB 可用 RAM，仅落盘可行（memory: cold） |
   | 4096d int8 | **121 GB** | 内存勉强，配合 memory 分层可 pinned |
   | 2048d int8（MRL） | 60 GB | 质量微损 |
   | 1024d int8（MRL） | 30 GB | 质量损更多 |
   | TurboQuant 4-bit（8×） | 60 GB | P0 实测召回损失后定 |
   | TurboQuant 2-bit（16×） | **30 GB** | 同上（e1 更正：原误写 15GB） |
   | TurboQuant 1-bit（32×） | 15 GB | 同上 |
   **换算基准（防串档）**：4096d fp32 = 16,384 B/点 × 29.5M 点 = 483GB 基准；上表 = 基准 ÷ 官方压缩率（fp16=2×、int8=4×、4bit=8×、2bit=16×、1bit=32×）
   另列独立预算：HNSW 图（29.5M×M=16 约数 GB，`hnsw_config.on_disk` 可外移）+ payload 索引（最小化后很小）+ 原始向量落盘（fp16 全量 242GB，/home 磁盘富余）
4. **链路拆分（N-4，修正原"蓝绿"表述冲突）**：① P1→P2 一次性续灌（**同一 collection**，无重复建设）；② 每日 updatefiles 增量 = **CPU 编码**（每日数千条量级，勿为此开 GPU 窗口）；蓝绿切换**仅**用于"全量重嵌"场景（如 FP8 重建），日常不用
5. payload 最小化（Q3 结论落地）：Qdrant 只存向量 + 最小过滤字段（PMID/年份/域编码）；**全量元数据（title/abstract/MeSH）留 Parquet**，按 PMID join——payload 数十 GB 会吃 RAM，且域标签重定义无需回灌向量库

## 7. 与记忆库 4B 服务的关系（N-11/N-12 调查结论，2026-09-25 20:07 实测）
